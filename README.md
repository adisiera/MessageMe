# MessageMe

A WhatsApp-inspired, independently branded, full-stack text chat application. TypeScript + React + Vite + Material UI on the frontend; TypeScript + Node.js + Express + WebSockets + SQLite on the backend.

## Requirements

- **Node.js 24+** and npm. Uses Node's built-in `node:sqlite`; no database service or native add-on installation is necessary. Node may print an experimental SQLite warning.
- Two separate browser profiles, or a normal and private window, to try two accounts.

## Quick start

```sh
npm install
npm run dev
```

Open **http://localhost:5173**. Create accounts in separate browser sessions, choose **New chat**, select a person, and start messaging. Select multiple people and provide a name to create a group. Accounts are not seeded.

The Vite development server proxies `/api` and `/ws` to Node on port 3001. Access through `localhost`, not `127.0.0.1`, unless you also update the allowed origins.

### Run the static frontend and backend together

```sh
npm run build
npm start
```

Open **http://localhost:3001**. The Node server serves the built SPA, API, and WebSocket endpoint from a single origin. The build must exist before starting the server. History and accounts persist in `server/data/messageme.sqlite`.

## Features

- Registration and sign-in, salted scrypt password hashes, opaque server-side sessions.
- HttpOnly, SameSite cookies; logout revokes the session and its live socket connections.
- Direct chats and named groups, searchable contact directory and chat list, unread filtering.
- Authenticated WebSocket text messaging, online presence, typing indicators and read receipts.
- SQLite message persistence, paginated history, reconnect with fresh server snapshots.
- Delivery acknowledgment, visible connection status, preserved unsent draft on failed delivery, and idempotent retries.
- Responsive Material UI layout, keyboard send (Enter), multiline messages (Shift+Enter).
- Backend and frontend Jest tests, plus real multi-user Chromium E2E tests.

## Tests

```sh
npm test
npm run build
npx playwright install chromium
npm run test:e2e
```

`npm test` runs server integration/Jest tests and React Testing Library/Jest tests. Tests use isolated in-memory or temporary SQLite databases. `npm run test:e2e` builds the frontend, starts a dedicated static server on port 3101 with an in-memory database, and tests messaging in independent browser contexts. It does not alter your local chat database. Browser downloads are needed only once.

The root dependency override requires patched `shell-quote` versions for development tooling. At validation time, `npm audit` still reports moderate development-only advisories through Jest's NYC loader (`js-yaml` / `argparse` / `sprintf-js`). These are not production runtime dependencies. Track upstream fixes rather than accepting npm's suggested downgrade to Jest 25. Run `npm audit --omit=dev` to check the deployed runtime dependencies separately.

If browser downloads are blocked, use an installed Chrome or Edge instead. For example, in PowerShell:

```powershell
$env:E2E_BROWSER_CHANNEL = 'msedge' # Or 'chrome'
npm run test:e2e
```

Additional commands:

```sh
npm run test -w server
npm run test -w client
npm run check
```

## Configuration

Set environment variables on the Node process (there is no automatic `.env` loader):

| Variable | Default | Purpose |
| --- | --- | --- |
| `PORT` | `3001` | HTTP and WebSocket port |
| `HOST` | `127.0.0.1` | Listening interface; use `0.0.0.0` only when intentionally exposing the server |
| `DATABASE_PATH` | `server/data/messageme.sqlite` | SQLite file; `:memory:` is useful for disposable runs |
| `APP_ORIGINS` | `http://localhost:5173,http://localhost:3001` | Comma-separated exact allowed origins for writes and WebSocket upgrades |
| `COOKIE_SECURE` | `false` | Set `true` behind HTTPS so cookies are never sent over plain HTTP |

Example in PowerShell, serving the built app on a different port:

```powershell
$env:PORT = '4000'
$env:APP_ORIGINS = 'http://localhost:4000'
npm start
```

For HTTPS deployment use a same-origin TLS reverse proxy that supports WebSocket upgrades, configure `APP_ORIGINS` to the public HTTPS origin, and set `COOKIE_SECURE=true`. The server deliberately does not trust forwarded client IP headers; rate limits behind a reverse proxy are shared unless you explicitly configure trusted proxy hops for your infrastructure. Do not enable arbitrary proxy trust.

## Architecture

```text
client/                 TypeScript React app, Vite config, Jest/RTL tests
server/src/             TypeScript Express API, authentication, SQLite schema, WebSocket hub
server/dist/            Compiled server output (generated by npm run build)
server/tests/           Jest HTTP and live WebSocket integration tests
e2e/                    Playwright multi-user and mobile tests
```

HTTP handles authentication, user search, conversations and history. WebSockets handle live messaging, presence, typing and read receipts. Both use the same cookie session and enforce membership. Message IDs order history; client-generated message IDs make retries idempotent.

### HTTP endpoints

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/health` | Readiness |
| POST | `/api/auth/register` | `{ name, email, password }` |
| POST | `/api/auth/login` | `{ email, password }` |
| GET | `/api/auth/me` | Current account |
| POST | `/api/auth/logout` | Revoke current session |
| GET | `/api/users?q=...` | Search display names; maximum 50 results |
| GET | `/api/conversations` | Member chats, unread counts, online peers |
| POST | `/api/conversations` | `{ memberIds, name? }`; group name required for multiple invitees |
| GET | `/api/conversations/:id/messages?before=...` | Latest/older 50 messages and `hasMore` |

### WebSocket protocol

Connect to `/ws` with the session cookie and a permitted Origin. Client JSON events:

```json
{ "type": "message", "conversationId": "...", "clientId": "unique-retry-id", "text": "Hello" }
{ "type": "typing", "conversationId": "...", "typing": true }
{ "type": "read", "conversationId": "...", "messageId": 42 }
```

Server events: `ready`, `conversation`, `message`, `typing`, `read`, `presence`, `error`. A `message` echo confirms that a message is saved. A read receipt means a member has opened that point in the conversation, not that every device has received it. Read receipts advance monotonically. Expired/revoked sessions close with code `4001`.

## Security and deployment boundaries

This is a production-oriented **foundation**, not a claim of production readiness or a WhatsApp clone with feature parity:

- **No end-to-end encryption.** The server can read messages. Use HTTPS/WSS outside localhost.
- Passwords must be 12-128 characters. Sessions expire after seven days. There is no password reset, email verification, MFA, account recovery, or account deletion flow yet.
- Users on a server can discover other users' display names and create chats with them. Contact invitations, blocking and abuse-reporting are not implemented.
- Membership authorization, parameterized SQL, origin checks, payload validation, request/event rate limits, heartbeat cleanup, and security headers are included.
- Text messages only: no calls, attachments, push notifications, message editing/deletion or membership management.
- This single-process SQLite/WebSocket design is not horizontally scalable. For multiple instances use a shared database, shared session storage and a pub/sub layer.
- Protect the database directory and back it up using a SQLite-aware backup strategy. Its contents include personal data and password hashes. Add operational logging, monitoring, recovery drills and deployment-specific hardening before real-world use.
